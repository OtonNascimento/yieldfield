## Maintainer decisions

**2026-07-10 — Execution-process simplification (applies to all work after
Plan 007).** One concise plan per feature; rely on the automated gates
(pytest, mypy, ruff, black, lint-imports, contract/client drift, frontend
gates) as the routine quality bar; ONE final review per slice instead of
independent per-task reviews. Independent micro-task reviews are reserved for
changes touching money paths, security surfaces, or tenant isolation. Plan 007
(in flight when this was decided) completes under the old per-plan review
protocol.

**2026-07-09 — Plan 006 spec (`docs/superpowers/specs/2026-07-09-dashboard-read-models-design.md`) §6 open questions: all four recommendations approved as-is by the operator.**

- **(a) Transition timestamps**: deferred from the first implementation. When
  "recovered this month" is commissioned, use an append-only
  `finding_transitions` table (finding_id, tenant_id, from_status, to_status,
  occurred_at, actor) — NOT a mutable `status_changed_at` column. Consequence
  for the first implementation: time windows bound detection time
  (`executed_at`) only.
- **(b) Severity ordering**: stable rank via a SQL `CASE` generated from the
  domain's `_SEVERITY_RANK`, with a unit test importing the domain map so DB
  ordering can never drift from it.
- **(c) Summary location**: `GET /api/v1/findings/summary` (no `metrics`
  resource). Must be registered before `GET /findings/{finding_id}`.
- **(d) Currency presentation**: strictly per-currency blocks; no primary-currency
  flag, no server-side conversion; single-currency tenants get a one-element list.

The follow-on implementation plan should stamp the spec's Status line
"Approved 2026-07-09" in its own commit (the spec lives in the 006 worktree
commit `39f1b9d`; editing it retroactively would churn a reviewed commit).
